# Constellation Defense 코드·도입 검토

검토일: 2026-08-10
범위: `D:\constellation-defense`, `D:\agentic-gamedev-playbook`, `D:\constellation-defense-submission`

## 결론

플레이북의 **방법론은 지금 도입하는 편이 좋다**. 현재 프로젝트는 이미 순수 엔진, 주입 RNG, 엔진 불변식 검사, 밸런스 봇, 절차적 3D·오디오라는 좋은 토대를 갖고 있다.

반면 플러그인 패키지 자체를 그대로 넣는 것은 권하지 않는다. 기존 것은 Claude용 `plugin.json`, `.claude-plugin`, `.claude` 설정을 사용한다. Codex에서 자동으로 활성화되지 않고, 제출물의 게임 런타임에도 아무 도움을 주지 않는다. 이 저장소에는 방법론을 프로젝트 전용 `AGENTS.md`로 이식했다.

MCP 서버는 의존성 없는 MIT 라이선스의 문서·프롬프트 제공 도구라서, 장기적으로는 선택할 만하다. 그러나 현재 서버가 제공하는 것은 플레이북 목차/섹션과 `new-game`, `balance-tuning`, `quality-pass` 프롬프트이며, 이 게임의 전술판 테스트나 밸런스 보정 자체를 실행해 주지는 않는다. 제출 전 우선순위는 MCP 연결보다 아래 P0 두 가지다.

| 대상 | 판단 | 이유 |
|---|---|---|
| 플레이북의 3-Gate·계층·검증 원칙 | 지금 채택 | 현재 코드 구조와 정확히 맞고, 제출 리스크를 줄인다. |
| 프로젝트 전용 `AGENTS.md` | 지금 채택 | Codex 작업 세션마다 같은 제품 경계와 검증 게이트를 유지한다. |
| Claude 플러그인 파일 복사 | 채택하지 않음 | Codex 패키지 형식이 아니며 이 저장소의 런타임과 무관하다. |
| 로컬 MCP 서버 연결 | 제출 후 검토 | 참고 문서를 빨리 찾는 이점은 있지만, 지금의 실제 품질 공백을 메우지는 못한다. |

## 현재 구조

```text
src/balance/  ← 적·용사·성·경제·필드 수치
src/engine/   ← 상태, 로스터, 경제, 전투·전술 효과의 순수 시뮬레이션
src/tactics/  ← 독립적인 3매치 보드 규칙(스왑·매치·보충·방어로 매핑)
src/app/      ← 저장소, 이전 수학 흐름, 별자리 전술판 화면·입력
src/gfx/      ← Three.js 월드·유닛·FX·환경
src/main.js   ← UI/오디오/렌더러/엔진 및 전술 보드의 배선과 고정 타임스텝
scripts/      ← 엔진·보드 불변식, 밸런스 봇, 기준선 검사
```

특히 `src/engine/`이 DOM과 렌더러로부터 분리되어 있고 `tick(state, dt) → events[]` 흐름을 사용하는 점은 강점이다. 저장 파일을 복원할 때 범위를 제한하고 잘못된 직업·겹친 발판을 방어하는 것도 좋다. `scripts/engine-check.mjs`는 배치/교환/조합/저장/별지기/승리·회차 규칙을 폭넓게 고정한다.

## 발견 사항

### P0 — 제출 설명과 코드의 현실이 갈라져 있다

제출 문서는 “교육형 수학 관문 제거”를 명시한다. 실제 조합 경로는 `doCombineDirect()`로 바뀌어 수학 문제를 열지 않으므로, 현재 플레이의 중심은 별자리 전술판이다. 하지만 이전 게임의 구현은 여전히 번들 및 여러 사용자 경로에 남아 있다.

- `src/main.js`가 `MathGen`과 `createMathFlow()`를 import·생성하고, 수학 모달 단축키·타이머·디버그 훅도 유지한다.
- `index.html`, `src/ui.js`, `src/app/store.js`, `src/balance/mathgate.js`, `src/mathgen/`, `scripts/math-check.mjs`가 남아 있다. `MathGen`을 `window.__game`에 노출하므로 번들러가 이 모듈을 제거할 수도 없다.
- 공유 카드는 아직 제목을 `용사 수학 디펜스`로 그리고 수학 정답률을 표시하며, 저장 파일명도 이전 게임 이름이다.
- `src/engine/state.js`에 수학 통계·저장 필드·메타 보상이 남아 있어 소스 검토 때 “제거” 주장을 약하게 만든다.

권장: 제출 전에 별도의 **수학 프로토타입 제거 마이그레이션**으로 이름·공유 카드·저장 스키마·UI·미사용 모듈·테스트·밸런스 봇을 함께 정리한다. 기존 localStorage/저장 파일을 유지할 필요가 있으면 읽을 때만 구버전을 허용하고, 새 저장에는 별자리 게임의 스키마만 쓴다.

### P0 — 밸런스 기준선이 실제 별자리 게임을 모델링하지 않는다

`scripts/balance-bot.mjs`는 조합 시 수학 레벨, 정답률, 힌트·재시도·수학 보상과 강화 수치를 시뮬레이션한다. 전투 중에는 기존 별지기 `castStar()`와 `castUlt()`만 사용하며 `castTactic()` 또는 보드 스왑을 전혀 호출하지 않는다.

따라서 `balance-baseline.json`의 통과는 현재 플레이어가 쓰는 3매치 전술의 난이도 보증이 아니다. 전술판이 핵심 루프인 제출물에서는 이 문제가 가장 큰 검증 공백이다.

권장: 전술 보드의 순수한 합법 스왑 탐지·결과를 만들고, 봇 프로필별로 위협 방어로·별 타입·4/5매치 선호를 다르게 둔다. 그런 뒤 기존 수학 행동을 제거하고 새 분포로 baseline을 다시 생성한다.

### P1 — 한 스왑의 서로 다른 매치가 하나로 합쳐진다

상태: 해결됨 (2026-08-10). `src/tactics/board.js`가 매치 셀을 같은 타입의 연결 컴포넌트로 분리하고, `src/app/tacticflow.js`는 이를 순서대로 해소한다.

한 번의 스왑에서 독립 매치가 여럿 나오면 각 그룹의 타입·크기·방어로를 유지한 채 별도 전술 명령으로 처리한다. 이 순수 규칙은 `scripts/tactic-board-check.mjs`에서 DOM이나 방어 엔진 없이 검증한다.

### P1 — 리셋 이후에도 예약된 연쇄가 새 보드를 건드릴 수 있다

상태: 해결됨 (2026-08-10). 전술판은 예약 타이머와 세대 번호를 관리하며, `reset()`에서 기존 연쇄를 취소한다.

전술판은 보류 중인 타이머와 보드 세대 번호를 함께 관리한다. `reset()`은 타이머를 취소하고 세대를 올리므로, 새 게임·불러오기·시련 뒤에 이전 연쇄가 새 보드나 상태에 적용되지 않는다.

### P1 — 전술 밸런스가 데이터 계층 밖에 있다

상태: 해결됨 (2026-08-10). `src/balance/tactics.js`가 Flare/Tide/Bloom 수치와 3·4·5매치 보정의 단일 출처이며, `src/engine/tactics.js`가 이를 방어 전술 명령으로 해석한다.

`src/engine/combat.js`는 더 이상 3매치 구현이나 전술 수치를 소유하지 않는다. 공통 피해·상태 이상은 `src/engine/effects.js`로 분리해 전투와 전술이 공유한다.

### P2 — 전술판의 엔진 계약 테스트가 없다

상태: 해결됨 (2026-08-10). `engine-check.mjs`는 Flare/Tide/Bloom, 웨이브 밖 잠금, 대상이 없는 길, 4·5매치 보정을 검사한다.

`scripts/engine-check.mjs`는 `castTactic()`의 타입별 효과·웨이브 잠금·대상 없는 길·4·5매치 보정을 고정한다. `scripts/tactic-board-check.mjs`는 DOM 없이 보드의 무매치 생성, 스왑, 독립 그룹 분리, 방어로 매핑, 보충 불변식을 고정한다.

## 권장 실행 순서

1. `src/ui.js`의 공유 카드와 저장 파일명부터 `Constellation Defense`로 바꾸고, 화면·카피에 남은 이전 게임 이름을 제거한다.
2. 수학 프로토타입을 한 번에 정리한다. 새 저장 형식/마이그레이션과 이전 기록 처리 방침을 먼저 정하고, dead import·모달·통계·메타·봇 경로를 함께 제거한다.
3. 실제 스왑 정책을 쓰는 밸런스 봇을 만든 뒤 baseline을 재측정한다.
4. 배포된 URL의 수동 플레이테스트와 실제 90초 영상 녹화를 진행한다.

이 순서는 플레이북의 “코어 루프를 실제 규칙으로 검증한 다음 마감·배포한다”는 원칙을 이 프로젝트의 제출 목표에 맞춘 것이다.
