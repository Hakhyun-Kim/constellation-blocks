# Constellation Defense AI GameDev Playbook

## 목적

AI는 기능을 많이 만드는 장치가 아니라, **가설을 빠르게 플레이 가능한 규칙·연출·검증으로 바꾸는 공동 개발자**다. 최종 재미와 제품 방향의 결정권은 사람에게 있다.

## 작업 원칙

1. 한 작업은 플레이어가 느낄 변화 하나로 시작한다.
2. 구현 요청에는 규칙, 비목표, 파일 경계, 수용 테스트를 함께 준다.
3. 규칙·밸런스·테스트·공개 문구가 달라지면 한 변경 단위에서 같이 검토한다.
4. AI의 제안은 코드·테스트·실플레이 중 최소 하나의 증거가 생기기 전에는 사실로 취급하지 않는다.
5. 런타임 모델 호출은 플레이어 가치를 분명히 늘릴 때만 넣는다. AI를 보이기 위해 API를 장식처럼 추가하지 않는다.
6. 외부 에셋은 품질을 높이는 정상적인 제작 수단이다. 라이선스와 출처가 명확하면 적극적으로 쓰되, 첫 플레이 속도와 프레임 성능을 기능과 같은 우선순위로 검증한다.

## 6단계 개발 루프

| 단계 | 사람이 결정할 것 | Codex가 맡기 좋은 일 | 완료 증거 |
|---|---|---|---|
| 1. 발견 | 플레이어가 겪을 문제와 30초 뒤의 감정 | 현재 코드·공개물·유사 기능 감사 | 한 문장 목표와 비목표 |
| 2. 설계 | 핵심 선택, 실패 조건, 밸런스 의도 | 모듈 경계·상태·이벤트 계약 초안 | 짧은 기능 명세 |
| 3. 수직 슬라이스 | 최소한의 첫 플레이 범위 | 엔진→UI→VFX→SFX·에셋 로딩까지 구현 | 직접 조작 가능한 한 장면 |
| 4. 검증 | 사람 플레이 기준과 허용 난이도·성능 예산 | 순수 테스트·시드 재현·봇·빌드·다운로드·프레임 검사 | 통과 로그와 실패 사례·전후 성능표 |
| 5. 플레이테스트 | 무엇이 헷갈렸고 무엇이 재미있었는지 | 관찰 정리·계측 지점·수정안 비교 | 우선순위가 붙은 메모 |
| 6. 출고 | 무엇을 공개하고 어떻게 설명할지 | README·영상 대본·체크리스트 | 공개 링크와 재현 가능한 기록 |

## 기능 요청 템플릿

```text
목표: [플레이어가 얻을 감정/선택]
비목표: [이번 작업에서 하지 않을 것]
규칙: [입력 → 상태 변화 → 결과 이벤트]
경계: [수정 가능한 계층과 수정하면 안 되는 계층]
연출: [무엇이 얼마나 빨리, 어디에 보여야 하는가]
에셋: [출처·라이선스·선로딩/지연 로딩·폴백]
성능: [초기 용량·첫 플레이 시간·FPS·p95 프레임·드로우콜 예산]
검증: [순수 테스트, 봇, 수동 스모크 항목]
완료 조건: [영상 또는 수치로 확인 가능한 결과]
```

예: “Tide 4등급은 한 방어로의 적을 더 오래 느리게 만든다. 줄 판정은 건드리지 않고, 밸런스·엔진 전술·VFX·테스트만 바꾼다.”

## 이 프로젝트의 계층 계약

```text
src/blocks/           블록 퍼즐 규칙: 판·조각·배치·줄 판정·트레이·방어로 매핑
src/engine/tactics.js 전술 명령: { route, kind, size } → 방어 상태·이벤트
src/engine/effects.js 공통 피해·상태 이상
src/app/blockflow.js  입력·DOM·미리보기·해소 타이밍
src/main.js           난수·전술 명령을 주입하는 유일한 브리지
```

새 기능은 아래 네 질문에 모두 “예”여야 한다.

- 외부 에셋을 포함한 최선의 제작 방법으로 플레이 품질이나 가독성이 실제로 좋아지는가?
- 모든 에셋의 상업 이용·수정·번들 배포 조건과 출처를 다시 확인할 수 있는가?
- 첫 플레이 다운로드와 전투 렌더링이 성능 예산 안에 있는가?
- DOM 없이 검증할 규칙, 결정적인 테스트 또는 같은 장면의 전후 측정이 있는가?

## 외부 에셋을 적극적으로 쓰는 방법

외부 에셋은 임시방편이 아니다. 영웅의 실루엣, 몬스터의 보행과 공격 예고,
지역 랜드마크, 무기·충돌·환경음처럼 사람이 즉시 품질 차이를 느끼는 부분에는
검증된 에셋을 우선 검토한다. 절차 생성은 배치·변형·색·파티클·규칙처럼 코드가
더 많은 다양성과 제어를 주는 부분에 집중한다.

### 채택 순서

1. 한 장면에 필요한 역할을 먼저 적는다. 예: 영웅 1명, 일반 적 2종, 중간보스,
   성문 랜드마크, 공격·피격음.
2. 같은 제작자·같은 시리즈에서 묶음을 우선 찾는다. 개별적으로 멋진 에셋 여러
   개보다 비례·재질·리그가 같은 묶음이 최종 품질이 높다.
3. 원본 판매/배포 페이지에서 상업 이용, 수정, 게임 번들 배포, 저작자 표시,
   재배포 제한을 확인한다. 검색 결과나 제3자 재업로드 설명만 믿지 않는다.
4. `assets/manifest.json`과 `CREDITS.md`에 증빙을 기록한 뒤 가져온다. AI 생성물은
   도구·플랜·생성일·약관 URL·입력 이미지 권리·사람이 수정한 부분도 기록한다.
5. Blender 등의 원본을 그대로 런타임에 넣지 않는다. GLB, 텍스처 아틀라스,
   압축 오디오처럼 브라우저용 결과만 배포한다.
6. 한 장면 파일럿을 현재 장면과 같은 시드·카메라로 비교한다. 품질 또는 가독성이
   분명히 나아지지 않으면 에셋 수를 늘리지 않는다.

manifest의 최소 형식은 다음과 같다.

```json
{
  "version": 1,
  "assets": [
    {
      "path": "assets/models/arin.glb",
      "creator": "Creator name",
      "sourceUrl": "https://original.example/asset",
      "license": "CC0-1.0",
      "licenseUrl": "https://creativecommons.org/publicdomain/zero/1.0/",
      "acquiredAt": "2026-08-13",
      "sha256": "64-character-lowercase-sha256",
      "preload": true
    }
  ]
}
```

### 거부 조건

- 라이선스가 없거나 ‘free’, ‘royalty-free’만 있고 상업 게임 번들 조건이 불명확하다.
- 타인의 캐릭터·브랜드·게임 화면을 생성형 도구의 입력으로 사용했다.
- 하나의 캐릭터만 아트 방향·해상도·재질이 다르다.
- 폴리곤·텍스처·오디오를 줄이지 않은 원본 때문에 첫 플레이가 느려진다.
- 원격 URL 핫링크에 의존해 원본 사이트 장애나 변경이 게임 실행을 깨뜨린다.

## 빠른 첫 플레이와 렌더링 성능 게이트

`npm.cmd run asset:check`는 다음 하드 예산을 검사한다.

- `index.html`, CSS, 최종 `dist/game.js`, 선로딩 에셋 합계: 원본 12MiB 이하.
- 전체 런타임 파일 합계: 원본 60MiB 이하.
- 단일 런타임 파일: 원본 8MiB 이하.
- `assets/`의 모든 파일: manifest 등록, SHA-256 일치, 출처·라이선스 증빙 필수.

에셋 변경은 자동 용량 검사만으로 끝내지 않는다. 같은 브라우저·같은 시드에서
기존 장면과 변경 장면을 각각 30초 이상 측정한다.

| 측정 | 데스크톱 high | 모바일 폭 lite | 회귀 기준 |
| --- | --- | --- | --- |
| 첫 조작 가능 시간 | 깨끗한 캐시에서 기록 | 깨끗한 캐시에서 기록 | 기존보다 20% 이상 느려지면 원인 분석 |
| 평균 FPS | 기존값과 비교 | 기존값과 비교 | 10% 초과 하락 금지 |
| p95 프레임 시간 | 기존값과 비교 | 기존값과 비교 | 20% 초과 악화 금지 |
| 드로우콜·삼각형·텍스처 | `renderer.info` 기록 | `renderer.info` 기록 | 이유 없는 증가는 병합 금지 |

첫 장면에 필요 없는 지역·보스·고해상도 음원은 지연 로딩한다. 로딩 중에도 첫
전투 조작은 가능해야 하며, 실패하면 절차형 폴백이나 재시도 UI로 복구한다.
품질 모드는 모델 정체성을 바꾸지 않고 해상도·그림자·파티클·후반 장식만 낮춘다.

## AI를 잘 쓰는 실제 방법

### 설계: 답 대신 비교안을 요청한다

AI에게 “재밌게 만들어 줘”라고 하지 않는다. 예를 들어 아래처럼 제약이 있는 비교를 요청한다.

```text
세 방어로와 6×6 보드는 유지한다.
플레이어가 5초 안에 이해할 수 있는 Tide 대안을 세 개 제안하라.
각 안에 선택, 반대 선택, 실패 가능성, 순수 테스트를 써라.
```

사람은 제안 중 게임의 정체성과 맞는 하나를 선택하고, 선택 이유를 기록한다.

### 구현: 작은 수직 슬라이스를 끝낸다

기능을 “보드 → 전술 → 렌더러 → 사운드 → 테스트”로 쪼개되, 각각을 따로 끝내지 않는다.
한 번에 플레이 가능한 얇은 조각을 만들고 바로 확인한다. 이렇게 하면 AI가 만든 코드가 연결 지점에서 어긋나는 일을 줄인다.

### 검증: 사람처럼 행동하는 봇을 만든다

AI는 플레이테스트 대체물이 아니다. 대신 반복 가능한 보조 도구다.

- 봇은 플레이어가 볼 수 있는 상태만 읽는다.
- 전술 보드를 쓰는 게임은 실제 합법 스왑과 전술 시전 정책을 포함한다.
- 보드·전투 난수는 주입해 시드 재현을 남긴다.
- 실패한 시드, 누수 방어로, 사용 전술을 저장해 밸런스 변경 전후를 비교한다.

### 연출: 감각은 사람이 판단하고, 반복은 AI가 돕는다

AI에게 “강한 타격감”을 요청할 때에는 피격 발생 시점, 지속 시간, 화면 위치, 색, 사운드 우선순위를 수치로 준다. 브라우저에서 실제로 보고 “읽히는가”를 사람이 결정한다. `dist/game.js`는 항상 소스 빌드 결과만 사용한다.

### 출시: 협업 과정 자체를 제품 증거로 만든다

각 중요 변경에 다음을 남긴다.

- 문제와 사람의 설계 결정
- Codex가 구현·분석·검증한 범위
- 관련 커밋과 실행한 테스트
- 실제 플레이 캡처 또는 영상 시점

이는 협업의 근거가 되고, 이후에는 재현 가능한 개발 기록이 된다.

## 런타임 AI 기능을 넣기 전 체크

다음 다섯 가지를 만족하지 못하면, 현재는 Codex를 개발 도구로만 쓰는 편이 낫다.

1. 모델이 없으면 만들 수 없는 플레이어 가치가 있는가?
2. 응답 지연·실패·비용이 있어도 게임이 안전하게 계속되는가?
3. 브라우저에 API 키를 넣지 않고 서버에서 비용·악용을 제어하는가?
4. 입력 데이터와 개인정보 사용을 플레이어에게 명확히 알리는가?
5. 결과를 재현하거나 최소한 효과 범위를 테스트할 수 있는가?

`Constellation Blocks`의 현재 최선은 런타임 모델 호출이 아니라, Codex로 빠르게 만든 명확한 실시간 전술 코어와 테스트 가능한 밸런스다. 나중에 AI를 넣는다면, 선택형 전투 회고·플레이 스타일 코칭처럼 게임을 멈추지 않고 결정의 이해를 돕는 기능부터 검토한다.

## 매 작업의 기본 게이트

```powershell
npm.cmd run engine:check
npm.cmd run blocks:check
node scripts/balance-check.mjs 60
npm.cmd run build
node scripts/asset-budget-check.mjs
```

밸런스 봇이 실제 블록 배치 정책을 쓰지 않는 상태에서는, 마지막 명령의 결과를 전술 밸런스 통과로 해석하지 않는다.

## 대형 기능 전후의 정리·품질 게이트

핵심 루프를 바꾸거나 둘 이상의 시스템을 가로지르는 기능은 구현 전후에 아래를 별도 작업으로 남긴다.

1. **구현 전 감산 감사:** 기존 UI·입력·저장·봇·테스트·카피를 제거/호환성·테스트용 격리/유지로 분류한다. 유지 항목에는 이유와 다음 책임자를 적는다.
2. **구현 후 품질 패스:** 데스크톱과 모바일에서 첫 1분과 새 루프 전체를 다시 플레이한다. 다음 행동·보상·실패가 바로 읽히는지, 정보 위계·국소 모션·피드백·입력 지연·성능·접근성의 개선 1~3개가 무엇인지 기록한다.
3. **출고 증거:** 결정적 엔진 테스트, 실제 플레이 규칙을 쓰는 밸런스 봇, 관련 수동 스모크를 다시 통과하고 제거·보류 항목을 문서화한다.

정상 경로가 한 번 동작한다고 완료가 아니다. 이전 흐름의 도달 불가 코드와 용어가 남아 게임이 "둘 다 반쯤"이 되는 것을 이 게이트에서 막는다.
